# NextSITREP remediation roadmap

Proposed **2026-11-05**, for review only. Baseline: commit **a6a7fdc** and the [consolidated register](AUDIT_RECONCILIATION.md). **No fixes, dependency changes, infrastructure or deployment are authorized by this document.** Existing C1/H1/H2-A protections must remain; H2-B requires the narrow R04 correction and affected-framework review. Keep the Next frontend and Spring backend separate.

Each numbered task is a reviewable change or evidence exercise with its own acceptance criteria. Prefer one task per PR; split further when a task crosses owners or cannot be verified independently. Dependencies below concern implementation order, not permission to implement now. Complexity **S** = bounded change/check; **M** = several related files or a focused integration test; **L** = integration work requiring smaller reviewed execution steps. These are relative estimates, not promised delivery dates.

## Acceptance stages

1. **G0 — approve the plan:** settle server topology, restricted synthetic Development scope, budget, database/recovery ownership and ingress identity. No AWS provisioning until separately approved.
2. **G1 — verified release candidate:** supported dependency baseline, nonces on HTML errors, effective CI/scanners, tested non-root images, Java 21 execution and actual PostgreSQL regression evidence. Passing local checks are the starting point, not this gate's completion.
3. **G2 — accepted AWS Development:** approved least-privilege delivery plus verified HTTPS/shared-origin/peer/secret/DB boundaries, restore/rollback, monitoring/capacity, and live-provider quota/readiness. Stub-only private verification may happen before live-provider acceptance. Restricted Dev contains synthetic data and named testers; it is not a public launch.
4. **G3 — public Production candidate:** all Production-Yes findings in the register closed or given an explicit reviewed alternative with equivalent protection, including authentication/privacy, trustworthy discovery and accessibility evidence. Rehearse promotion into the separate Production account; no production secrets/data copied into Development.
5. **G4 — measured improvement:** optional performance, cleanup and product decisions. Elevate a task if capacity tests or new evidence reveal a blocker. Do not add Redis, Kubernetes, service decomposition or paid controls merely for hypothetical scale.

The existing [H2-C staged plan](architecture/aws-deployment-plan.md) supplies infrastructure detail. Its steps are proposals, not completed deployments. A $30–40 target is not an authorization to omit backups, SSR, TLS or monitoring. Requote the approved model before provisioning; scheduled Development is an alternative to an unrealistic always-on budget, not a database deletion policy.

## Completion discipline

- Update the single canonical register with the PR/commit, exact changed source and test/deployment evidence. Historical IDs stay aliases; do not create duplicate projects for them.
- Keep the 70% JaCoCo gate and add meaningful boundary tests; aggregate coverage is not a replacement for persistence/ownership/real-ingress proof.
- For frontend changes run relevant tests, lint/format checks, TypeScript and production build. For backend changes run relevant tests and Maven verify on Java 21. Re-run container/ingress or PostgreSQL tests only where the change affects those boundaries.
- Track an owner, next evidence needed and review date for Needs Verification items. An unknown becomes neither Fixed nor a demonstrated exploit merely because a release date approaches.
- Approve documented residual risk only with scope, compensating control, owner and expiry. Cost pressure is not a compensating control. Leave architecture/account/production decisions to explicit review.
